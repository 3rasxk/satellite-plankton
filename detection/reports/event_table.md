Reading this honestly, by real cause:

- **th_003 (2009-03), th_008 (2010-07), th_012 (1981-02), th_014 (1983-05):** predate Sentinel-2's launch (2015-06-23). There is structurally no Sentinel-2 scene to find for these dates -- not a cloud rejection, not a search-window problem. th_012/th_014 also predate MODIS-Aqua's 2002 archive start for their own historical year, yet MODIS climatology is a day-of-year pool across *all* archive years, so it was still attempted and returned real numbers for th_014 (n=10, reliable) -- the seasonal baseline is checkable even when the specific historical year's own reading is not.
- **th_004 (2016-01, Cha-am Coast):** within the Sentinel-2 era, but zero scenes were returned by the Earth Engine collection query for the entire recorded month at this point -- an early-era tiling/coverage gap for this specific location, confirmed by a direct collection query, not a cloud rejection. MODIS climatology did return a value here (n=1, flagged unreliable by `climatology.py`'s own `MIN_RELIABLE_N=5` threshold).
- **th_006 (2019-08-27, Koh Loy):** Sentinel-2 scenes genuinely exist -- 20 candidate images were confirmed in the searched window by a direct collection query -- but every one was cloud-rejected (`cloud_fraction` over the `max_cloud_fraction=0.5` limit); this is real, heavy Aug-2019 monsoon-season cloud cover, not a missing-scene problem. MODIS climatology also returned no data at this coordinate.
- **th_010 (2020-02-11..20, Ang Sila): the one event that now produces a real reading.** Earlier versions of this report recorded it as failing the JRC Global Surface Water land/water mask at every radius from 30 to 250 m and called that "a real site characteristic", quoting the error text as the evidence. That was wrong: the error was a defect in this pipeline (JRC has no data over open ocean and the mask read that as land -- see LIMITATIONS.md 5), not a property of the site. With the mask fixed it returns Sentinel-2 bands at 30, 50 and 100 m, and MODIS climatology returns a real, reliable value (n=6). It is still not a calibration set: n=1, the species is karenia_sp rather than the Noctiluca the B2/B3 feature targets, and the reading exists only via the ETOPO1 fallback over a buffer whose brightness is consistent with a turbid pier strip. The coordinate was never adjusted to force a fit.

**Net result: 1 of these 7 events produces a real matched (index_value, z-score) pair** -- the other six fail for six different, individually verified reasons, not one blanket failure. This is a materially different finding from the earlier "0 of 14, no coordinates at all": these 7 have real, confirmed coordinates and were genuinely queried; the limitation has moved from *location* to *satellite data availability at that location/date*, which is itself useful information about where this pipeline can and cannot currently operate (pre-2015 dates, this specific river-mouth tiling gap, this specific near-shore mask limitation).

## Reading this table honestly

- **7 of 14 events have lat/lng in `events.csv`** (7, added 2026-08-22, human-sourced from public references and confirmed by the maintainer -- see events.csv's own citation text per row). The remaining 7 (th_001, th_002, th_005, th_007, th_009, th_011, th_013) are still deliberately unmatched -- per `docs/DETECTION_PLAN.md` §3, a coordinate is never invented for a named place.
- **1 of 14 events produced a real matched (index_value, z-score) satellite reading in this run** -- see 'The 7 newly-coordinate events' section above for the real, individually verified reason for each of the 7 that were actually queried and still did not produce a usable reading (four predate Sentinel-2's 2015 launch, one is a genuine early-era tiling gap, one is genuine monsoon cloud cover, one is a genuine near-shore land/water mask limitation).
- th_001's regional-proxy attempt (still no coordinate of its own) found no usable Sentinel-2 scene and a real ~2-month MODIS data gap around the event date -- unchanged from the prior phase.
- Every leave-one-out iteration above therefore still reports `caught = n/a` -- not because no member had a coordinate (7 do, now), but because none of those coordinates yielded a real satellite reading this run, for the documented reasons above. `thresholds.leave_one_out`'s cluster partial-match rule (OR across matchable members) is fully implemented and will produce a real `caught=True/False` the moment any cluster member does yield a real reading.
- th_012/th_013/th_014 (marked in the low-evidentiary-weight column) are pre-monitoring-era with no cell count in any source (`data/validation/CALIBRATION_NOTES.md` §3) -- shown in the table for completeness, never averaged into a headline number with the 9 cell-count-bearing events.
- **No percentage is reported anywhere in this table or this file, by design** (CLAUDE.md truth boundary, `.claude/agents/bloom-detection.md` "Non-negotiable rules").
